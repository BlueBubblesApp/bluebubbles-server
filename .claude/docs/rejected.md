# Rejected approaches

Designs that were tried and abandoned, or proposed and turned down, each with the reason and
the page that argues it. Read this before proposing a redesign. If your idea is a row here,
the row says what would have to change for it to be right, and that is the argument to make.

This is an index, not the argument. Each row states the reason in a sentence and links to
where it is made in full, which is the one place it lives
([`WRITING.md`](../../docs/WRITING.md) rule 8). A row whose link goes stale fails
`DocumentationDriftTests`.

## Add a row

Add a row when an approach is reverted, when a design is turned down in review, or when you
argue one out of a change before writing it. Write it in the same change, under the date it was
rejected, in `YYYY-MM-DD` form.

- **Approach** is what someone would propose, in their words, so a search for the idea finds it.
- **Why not** is the failure it causes, not the preference against it.
- **Reopen if** is the fact that would change the answer, or `—` when nothing would.
- **Argued in** links to the paragraph that holds the reasoning. When no page holds it yet,
  write the paragraph in [`decisions.md`](decisions.md) first and link to that.

Rows dated 2026-11-01 come from the import of the Swift tree, whose history is a single
commit: those approaches were rejected on or before that date.
